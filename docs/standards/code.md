# Code standards

Why the code rules exist. Where a check enforces a rule, its failure message says enough to fix
the problem without this page. Read this page when a rule seems wrong, or when a review asks
for something no check covers.

| Rule                                                                   | Enforced by                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Packages never import what the import matrix forbids                   | `pnpm lint` (`no-restricted-imports`, generated by `scripts/lint-config.ts`)         |
| `packages/core`, `packages/protocol` and `apps/web` stay platform-free | `pnpm lint` (`import/no-nodejs-modules`)                                             |
| No import cycles                                                       | `pnpm lint` (`import/no-cycle`)                                                      |
| Only `packages/host-guard` runs tmux or sends a signal                 | `pnpm lint` (`bazhen/host-guard`, `scripts/lint-plugin.ts`)                          |
| Only erasable TypeScript (no enums, namespaces, parameter properties)  | `pnpm typecheck` (`erasableSyntaxOnly`)                                              |
| No `any`; switches over unions are exhaustive                          | `pnpm lint`                                                                          |
| No floating or misused promises                                        | `pnpm lint` (type-aware)                                                             |
| Lint warnings and unused suppressions fail                             | `pnpm lint` (`--deny-warnings`, `--report-unused-disable-directives-severity=error`) |
| Errors at seams are typed; nothing is swallowed                        | review                                                                               |
| Comments explain _why_, never _what_                                   | review                                                                               |
| Dependencies are pinned exactly, with a reason for any pre-release     | review                                                                               |
| The committed JSON Schema matches the protocol's zod schemas           | `pnpm check` (`scripts/protocol-schema.ts --check`)                                  |

## Boundaries

The domain is in `packages/core`. It knows nothing about tmux, node-pty, Hono, SQLite or the
browser, so it can be tested in memory and moved to another runtime unchanged. Everything
platform-specific sits behind a seam: an interface defined in core, with one implementation in
an adapter package or in `apps/daemon`.

Each layer has one job:

- `packages/core` is the domain: entities, state machines and the seam interfaces.
- `packages/protocol` is the shared types and schemas that cross the network.
- `packages/runtime-tmux` is an adapter: it implements a core seam on tmux.
- `packages/host-guard` is the only code that runs tmux or sends a signal, product and tests
  alike. `TmuxServer` names every server by a socket path inside a directory its caller owns,
  never by `-L`, and refuses `default` and the directory the user's own servers share. A signal
  reaches only a group this process started (`spawnGroup`), a pane its tmux server vouched
  for (`paneGroup`, `signalPane`), or one of its own tmux servers, with `SIGUSR1` alone, once
  `ps` shows that pid is the server on that socket, started when its refs recorded
  (`recreateSocket`, `signalServer`). It depends on nothing of Bazhen's, so anything may use it.
  The one signal sent elsewhere is `ChildProcess.kill()` on a child this process spawned and still
  holds: Node addresses it by the child's own pid, so it can't reach anything else.
- `apps/daemon` is the composition root: it wires the adapters and implementations into core.
- `apps/web` is the client: it talks to the daemon only through the protocol.

The allowlist is each package's `package.json` dependencies: pnpm lets a package import only
what it declares. Lint adds what `package.json` can't express: Node built-ins, type-only
imports, and imports by relative path into another package. The matrix data is `MATRIX` in
`scripts/lint-config.ts`, and a medium test fails if a `package.json` declares a workspace
package its area bans. Change the matrix there, run `pnpm lint:config`, and commit both files.
Moving a package boundary is a design change, so say why in the commit.

## TypeScript

The daemon runs `.ts` files directly through Node's type stripping, with no build step in
development. Anything Node can't strip fails `pnpm typecheck`, and the fix is always the same:

- use a union of string literals instead of an `enum`;
- use a module instead of a `namespace`;
- assign fields in the constructor body instead of using parameter properties.

Imports use the `.ts` extension. `import type` is for types only, because
`verbatimModuleSyntax` keeps every value import at runtime.

## Errors

- **Expected failures at a seam are typed.** Examples are a schema newer than this build
  (`SchemaTooNew`) or an event the state machine rejects (`InvalidTransition`). Throw a named
  class with the fields a caller needs to decide what to do, or return a discriminated union
  when every caller must handle the case. Don't throw a bare `Error` with a message to parse.
- **Wrap third-party errors at the seam.** A raw `execFile` or SQLite error that escapes an
  adapter leaks the implementation into the domain. Catch it at the adapter boundary and
  rethrow it typed, keeping the original as `cause`.
- **Never swallow an error.** If a failure is really harmless, handle it explicitly and say why
  in a comment. Otherwise let it propagate.
- **Validate at network boundaries.** Every request and response body goes through its zod
  schema in `packages/protocol`, at the daemon's edge, in both directions.
- **Publish the protocol.** `packages/protocol/schema/` is the protocol as JSON Schema, generated
  from every zod schema `packages/protocol` exports, for clients in other languages. After
  changing a schema, run `pnpm schema` and commit the files with it.

## Comments

Default to none. A comment earns its place when the reason for the code can't be read from the
code itself: a tmux defect being worked around, a measured limit, or a choice that looks wrong
but isn't. Never narrate what the next line does. Keep ticket numbers and incident stories in
the commit message, not the code.

## Dependencies

Pin exact versions and commit the lockfile. A pre-release pin, such as node-pty
`1.2.0-beta.18`, carries a comment naming the measured reason and the stable release that
replaces it. Upgrade one foundational dependency per commit.
